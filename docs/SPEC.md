# Қalta — спецификация

## Цели
Личный трекер финансов: расходы/доходы, долги, категории — с локализацией (ru/kz/en), кастомизацией темы/акцента, и опциональной синхронизацией между устройствами через Google-аккаунт.

## Не-цели
- Не банковское приложение: нет интеграций с реальными банками/платёжными системами, нет обработки платежей.
- Не многопользовательская платформа: каждый пользователь видит только свои данные, нет общих/командных пространств.
- Не серверное приложение: нет собственного бэкенда — только статический клиент + Firebase (BaaS) как опция.

## Пользователи
Один человек на аккаунт. Вход опционален: без входа — данные в localStorage этого браузера; со входом через Google — синхронизация через Firestore, привязанная к Google-аккаунту.

## Данные и чувствительность
- Категории трат, суммы операций, заметки, долги (имя/сумма/срок), настройки темы, язык.
- **Не собирается**: пароли (аутентификация полностью делегирована Google/Firebase Auth), платёжные реквизиты, номера карт/счетов.
- Из PII при входе через Google хранится: email, отображаемое имя, аватар (стандартный профиль Firebase Auth) — используется только для показа «Вошли как …», никуда не отправляется.

## Платформа
Web PWA (устанавливается на домашний экран телефона). Один HTML-файл + статические ассеты (иконки, manifest), хостится на GitHub Pages. Работает офлайн (данные в localStorage); Firestore-синхронизация требует сети и no-op'ится при её отсутствии.

## Архитектура (адаптированный стек)
- **Клиент**: один самораспаковывающийся HTML-файл. Внутри — компонент на кастомном рантайме (`dc-runtime`, React без сборщика, JSX-подобный шаблонизатор `sc-if`/`sc-for`/`{{ }}`). Не Next.js/Vite — сознательный выбор: это уже существующий, протестированный формат, переписывать его в другой стек означало бы выбросить всё сделанное без функциональной выгоды для статического PWA такого размера.
- **Хранилище**: localStorage (всегда) + Firestore, один документ на пользователя `users/{uid}` (опционально, при входе).
- **Авторизация/аутентификация**: Firebase Authentication, только Google-провайдер. Никакой самописной криптографии/хэширования — делегировано Google/Firebase.
- **«Сервер»**: Firestore Security Rules — это и есть точка серверной проверки прав в этой архитектуре (клиент пишет напрямую в Firestore, но только в рамках того, что разрешают правила).
- **Хостинг**: GitHub Pages — статика, HTTPS обязателен и включён по умолчанию GitHub'ом. Нет доступа к серверным HTTP-заголовкам — CSP и другие security-заголовки заданы через `<meta>` в самом HTML.

## Ключевые сценарии (проверены вручную, см. docs/VERIFICATION.md)
1. Добавить расход/доход с категорией, способом оплаты, датой.
2. Отредактировать/удалить операцию (свайп или долгое нажатие).
3. Добавить долг, частично погасить, полностью закрыть, восстановить закрытый.
4. Управлять категориями: переименовать, задать цвет/размер плитки, удалить (с переносом операций в «Прочее»/«Прочий доход»), перетащить для сортировки.
5. Сменить тему (светлая/тёмная), акцентный цвет, стиль интерфейса, язык.
6. Экспортировать/импортировать резервную копию (.json).
7. Войти через Google → данные синхронизируются между устройствами; выйти → остаются только локальные.
8. Чужой пользователь (другой Google-аккаунт) не может прочитать/изменить документ первого — обеспечивается Firestore Rules, см. `firestore.rules`.

## Критерии приёмки
- Все сценарии выше работают без ошибок в консоли, на светлой и тёмной теме, на ru/kz/en.
- Приложение остаётся полностью функциональным при `QALTA_FIREBASE_CONFIG = null` (Firebase не настроен) — деградация без поломки.
- Contrast ratio ≥ 4.5:1 для текста, все интерактивные элементы ≥ 44×44px, доступны с клавиатуры, иконки-кнопки имеют `aria-label`.
- Нет секретов в репозитории (grep-проверка).
