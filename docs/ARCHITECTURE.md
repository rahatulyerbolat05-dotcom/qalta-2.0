# Архитектура

## Файлы репозитория
```
index.html            # вся раскладка + весь код приложения (self-extracting bundle)
firebase-config.js     # публичный конфиг Firebase; null = синхронизация выключена
firestore.rules        # правила доступа: пользователь видит только users/{свой uid}
manifest.json           # PWA-манифест
icons/                  # иконки приложения (favicon → 512px + maskable)
docs/                   # эта документация
```

## Почему один HTML-файл, а не Next.js/Vite
`index.html` — это экспорт из среды прототипирования: внутри `<script type="__bundler/manifest">`/`<script type="__bundler/template">` лежат сжатые ассеты и шаблон приложения, которые при загрузке страницы распаковываются в реальный DOM (см. комментарии в верхнем `<script>` файла). Само приложение написано на кастомном мини-рантайме `dc-runtime` поверх React: `<sc-if>`/`<sc-for>` — условный рендер и списки, `{{ выражение }}` — интерполяция, `class Component extends DCLogic` — компонент с `state`/`setState`/`componentDidMount`/`componentDidUpdate`.

Это уже рабочий, протестированный формат для статического PWA такого размера. Пересборка на Next.js добавила бы сборщик, роутинг и SSR, которые тут не нужны (нет бэкенда, нет страниц кроме одной), и потребовала бы переписать весь код заново без функциональной выгоды. Решение — оставить формат, поднять качество внутри него.

## Поток данных
```
state (React state в Component)
   │
   ├─→ localStorage["qalta-proto-v1"]   (всегда, синхронно на каждое изменение)
   │
   └─→ Firestore users/{uid}            (только если вошли через Google;
                                          debounce 900ms, см. fbMaybePush)
```
При входе — одноразовое чтение `users/{uid}` и merge в state (Firestore считается источником правды на момент входа). Нет постоянной live-подписки (`onSnapshot`) — сознательное упрощение: конфликт «два устройства одновременно» не разрешается в реальном времени (last-write-wins при следующем изменении), что приемлемо для личного трекера, которым обычно пользуются с одного устройства за раз.

## Авторизация
Firebase Authentication, провайдер Google (`signInWithPopup`). Токены и сессия — под управлением Firebase SDK (свой storage, не localStorage приложения). Приложение хранит из профиля только `uid`, `displayName`/`email`, `photoURL` — для UI, не передаётся никуда за пределы Firebase.

## Модель данных Firestore
Один документ `users/{uid}` на пользователя, поля — точное зеркало того, что уже пишется в localStorage: `ops`, `debts`, `closed`, `eCats`, `iCats`, `hex`, `skin`, `set`, `lang`, `light`, `catColors`, `catSizes`, `lastSync`. Схема не нормализована (не отдельные коллекции per-operation) — оправдано объёмом данных личного трекера (десятки-сотни операций, не миллионы) и тем, что вся модель и так загружается в память клиента целиком.

## Security Rules (см. `firestore.rules`)
`allow read, write: if request.auth != null && request.auth.uid == uid` — пользователь может обращаться только к своему документу. Плюс ограничение размера/формы документа, чтобы аутентифицированный клиент не мог записать произвольно большой блоб (см. комментарии в файле правил).
